# Stage 03.1r — Build on the user's real tables (READ-ONLY)

Run this **instead of `03.1-build.md`** when the project is grounded on the user's own data
— i.e. **`PROJECT/specifications/source-tables.md` exists** (the home page's "Use existing
data" flow; the opening message says so). The demo is built **DIRECTLY on those real Unity
Catalog tables, read-only**: you query them **in place** and build read-only analytics on
top. You do **NOT** generate synthetic data.

If **`PROJECT/specifications/data-discovery.md`** exists, it captured the use case the user
**chose during data discovery** (+ its data-fit rationale and the join keys/signals from
`source-tables.md`). The Stage-1 story + specs should already reflect it — build to that
agreed use case; if a spec drifted from it, fix the spec, don't silently build something else.

Everything about the *build loop* is the same as `03.1-build.md` — walk the numbered spec
files in `PROJECT/specifications/`, use the matching Databricks Agent Skill (DAS) per
resource, validate, and record the real ID in `resources.json.created_resources` only after
it exists. The **Behavior rules**, **Build-order gate**, and **How to build** recipe in
`03.1-build.md` all apply here. This file only changes **Step 1** (the data foundation) and
narrows the capability set.

## The one non-negotiable rule

**The user's real tables are READ-ONLY. Forever.** Never `INSERT`/`UPDATE`/`DELETE`/`MERGE`,
never `ALTER`/`DROP`, never `CREATE ... AS SELECT` into them, never rename or re-catalog
them. Every component reads them with `SELECT` only. If a spec seems to require writing to a
real table, that spec is wrong — stop and fix it (or drop the capability). This holds even
under the data-write opt-in below.

---

## Step 1 — Verify the real tables, declare them as the foundation (NO data generation)

There is no data-gen script and no pipeline here. `01-lakeflow.md` for a grounded demo is a
**"Source tables (read-only)"** spec listing the real fully-qualified names. Instead of
generating data:

1. **Confirm every real table is readable.** For each `catalog.schema.table` in
   `specifications/source-tables.md` / `01-lakeflow.md`, run a quick `SELECT COUNT(*)` (and
   a `SELECT * ... LIMIT 5` if useful) via the SQL warehouse (use the query CLI the
   `databricks-dbsql` / analytics DAS documents — **not** Databricks Connect serverless).
2. **Profile the tables (read-only) to understand the data.** `source-tables.md` lists the
   **schema only** — gather the profile yourself: distinct counts, null %, ranges, and top
   categorical values, then derive the capability signals (time columns, numeric measures,
   low-cardinality dimensions, cross-table join keys). See
   `DEMO_SKILL_DIR/references/grounding-table-stats.md` for the exact queries and how to turn
   them into a use-case fit read. This is how you choose the measures, time axes, dimensions,
   and joins your read-only build runs on.
3. **If a table is missing, empty, or permission-denied, STOP.** Report which table and why
   to the user; do not silently substitute or synthesize. A grounded demo with no readable
   data is a real blocker, not something to paper over.
4. **Record the sources.** These real FQNs ARE the data foundation — do not add them to
   `resources.json.created_resources` (you didn't create them). The downstream specs already
   reference them; your job is to point each built resource at those exact names.

**Gate before Step 2:** every real table a downstream spec references returned rows.

### Data-write opt-in (only if the user opted in)

If — and only if — `source-tables.md`'s header (or the opening message) says the user
opted into letting the demo add its own supporting data, you MAY create **auxiliary** tables
that write-needing capabilities require (e.g. an app's write-back table, an ML feature/label
table). Rules:

- Create them in the **demo's OWN** catalog/schema (the one in your system prompt's
  Resources section), **never** in the user's catalogs. Label them clearly as demo-created
  in the spec.
- Prefer deriving them **from the real tables via read-only `SELECT`** (e.g. a materialized
  aggregate) over pure synthesis, so the demo stays grounded in the real data.
- The real tables remain read-only — auxiliary tables are additive, in a separate namespace.

Absent the opt-in: **create no tables at all.** The capability set is read-only analytics
(dashboards, Genie, metric views, read-only AI functions).

---

## Step 2 — App (only under the data-write opt-in, and only if an app spec exists)

A read-only demo normally has **no app** (an app implies write-back / its own datastore). If
the user did NOT opt into data-write, there will be no `specifications/app/` — skip straight
to Step 3.

If the user opted in AND `specifications/app/` exists, spawn the App subagent exactly as
`03.1-build.md` Step 2 describes (same spawn prompt, same completion contract, same
late-fill rules) — with one addition to the prompt: **the app queries the real tables
read-only and may only write to the demo's own auxiliary tables; it must never write to the
user's real tables.**

## Step 3 — Walk the remaining specs on main (in numbered order)

Same as `03.1-build.md` Step 3, restricted to the read-only-friendly resources the story
uses. Point each at the real FQNs from `source-tables.md`:

- `02-uc-governance.md` — UC **grants / metric views / row-level security** over the real
  tables (all read-side; no writes).
- `04-ai-bi.md` — **Genie space** then **dashboard** (sequential), built on the real tables.
  Invoke the `databricks-aibi-dashboards` DAS; cross-reference
  `DEMO_SKILL_DIR/references/blocks/capabilities/aibi-dashboards.md`.
  - **Lift a LuxeBeauty dashboard as the layout starting point** —
    `DEMO_SKILL_DIR/references/example-luxebeauty-simple/dashboard/dashboard.json` (or the
    fuller `example-luxebeauty/dashboard/dashboard.json` for a richer multi-table build): a
    worked, tabbed, color-pinned structure to copy and swap the real tables/columns/story
    into. It's a reference, not a fill-in template — lift only what this story needs.
  - **Match the use case's scope — don't silently shrink it.** Build on the tables the chosen
    use case actually spans (its `datasources` in `data-discovery.md`); if the plan says 8
    tables, use them — as Genie data sources and dashboard widgets — rather than collapsing to
    the 2 the headline sentence happens to join.
  - **Validate rendering, not just the query:** after deploying, confirm every widget actually
    shows data. The blank-widget / titleless-card gotchas and the field-binding checklist live
    in the `databricks-aibi-dashboards` DAS and `aibi-dashboards.md` — follow them there.
- `metric-views` — governed metrics defined over the real tables.
- Read-only **AI functions** (`ai_query`, `ai_classify`, …) applied to the real data in
  queries, if the story uses them.
- ML/KA/MAS: only under the data-write opt-in (a KA needs its own vector index; ML training
  needs feature/label tables) — build those on auxiliary tables, never by writing to the
  real ones.

Validate each resource (rows returned, endpoint answers) and record its ID in
`resources.json.created_resources` only after it exists.

## Final review

Confirm: every built resource points at the **real** `catalog.schema.table` names; **no new
catalog/schema was created** for the user's data (no `ai_demo_gen` or similar); the real
tables were only ever read; all created resources are recorded in `resources.json`; and no
leftover template example content remains anywhere. If the user opted into data-write, any
auxiliary tables live in the demo's own catalog and are labeled as demo-created.
